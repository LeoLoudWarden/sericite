# VM handle

`VMHandle` is the Python host's public entry point for observing and controlling one VM. It is returned by [`SericiteEngine.create_root`](01-engine-and-limits.md#sericiteenginecreate_root), is bound to the engine that created it, and should not be instantiated directly.

The handle returned by script-side `VM()` shares most of the state and driving semantics, but host snapshots, file management, and resource metering differ. The authoritative description of the script's common contract is the [script VM reference](../../scripting/reference/06-vm.md).

## States

| State | Meaning | Terminal |
|---|---|---|
| `ready` | Not yet started, or ready to continue | No |
| `waiting_input` | Waiting for input that may arrive later | No |
| `paused` | Paused at a statement-entry breakpoint, with recoverable execution state | No |
| `done` | The current program completed normally | Yes |
| `error` | The current program terminated with an ordinary error | Yes |
| `resource_exhausted` | The current program terminated because a resource quota was exhausted | Yes |
| `terminated` | Terminated, or terminated by cascade disposal | Yes |

Empty source can be `done` immediately after creation. A terminal state does not mean the handle is invalid: you can still read snapshots and stdout, manage breakpoints, take back the VFS, or dispose.

There is no readable `disposed` state after disposal. After disposal, handle operations other than repeated `dispose()` raise `runtime_error`.

## VMHandle.run

```python
vm.run(inputs: list[str] | tuple[str, ...] | None = None) -> str
```

Drive the target until it completes, waits for input, hits a breakpoint, or fails. Returns the target's currently retained cumulative stdout, not just the text newly produced by this call.

The whole batch of strings in `inputs` is added to the target's input queue first. A target in `waiting_input` changes to `ready`; input can also be preset early in other states.

- A return does not mean the state is necessarily `done`; identify `waiting_input` or `paused` through the snapshot.
- With `buffer_output=False`, it returns an empty string, while output forwarding and observation events still occur.
- Script errors propagate to the host as `SericiteError`; output already produced is not retracted because of this.
- Nested driving is rejected when the same VM is already being driven.
- Invalid input values are rejected with `SericiteError`; non-strings are not added to the queue.

## VMHandle.exec

```python
vm.exec(source: str) -> str
```

Compile and deliver new source, execute it immediately in the same module scope, and return only the buffered output newly produced by this delivery.

Module-level variables, functions and schemas, the loaded-module cache, addons, the VFS, the module resolution root, the input queue, output configuration, breakpoints, and accumulated resource usage are retained. The root's `argv` also persists.

`exec()` discards the old program that has not finished executing, including execution states that never started, are waiting for input, or are paused at a breakpoint; the old error and debug frame stack are replaced. Call `snapshot()` first when you need to keep the old program state. Do not use `exec()` as a substitute for input recovery or breakpoint recovery.

Compilation happens before any state change: when compilation fails, the original program, the paused execution state, and the breakpoint bindings stay as they were. After a successful delivery, main-path breakpoints bind to the new main source by the same line numbers and do not hit functions left over from the old delivery.

A target that is `terminated`, has had its VFS taken, or is currently running rejects delivery. `source` must be a string and follows the same 4 MiB UTF-8 source limit as root creation.

## Input

### VMHandle.feed_input

```python
vm.feed_input(value: str) -> None
```

Add one line string to the target's input queue. A target in `waiting_input` changes to `ready`, but this method does not actively execute the target; call `run()`, `step()`, or `step_instruction()` afterward to continue.

### Input at creation

The contracts of `create_root(inputs=...)` and `input_provider` are in the [engine creation parameters](01-engine-and-limits.md#input-and-output). The provider's pause and `input_error` rules do not change the ownership of the methods in this section.

## Stepping

### VMHandle.step

```python
vm.step() -> dict[str, object]
```

Execute one statement and return a [host snapshot](#snapshot). Statements inside function calls and breakpoints may affect the actual stopping location. A target already in a terminal state does not advance and only returns the snapshot; a target in `paused` resumes, and the current breakpoint is exempted only once.

### VMHandle.step_instruction

```python
vm.step_instruction() -> dict[str, object]
```

Execute one Sericite internal instruction and return a host snapshot. The terminal-state and breakpoint-resume rules are the same as `step()`. Internal instructions are a debugging granularity, not a public operation API in script source.

## Output

### VMHandle.stdout

```python
vm.stdout() -> str
```

Return the target's currently retained cumulative stdout without advancing execution. With `buffer_output=False`, it returns an empty string.

For the ordering among output buffering, the writer, and observation events, see [execution sessions and virtual IO](../guides/02-sessions-and-io.md#forwarding-output-live) and [observation events](05-observation.md#event-kinds).

## Breakpoints

### VMHandle.add_breakpoint

```python
vm.add_breakpoint(line: int, path: str | None = None) -> None
```

Add a statement-entry line breakpoint. `line` must be a strict integer greater than zero; `bool` is not accepted. `path` is `None` or a logical path normalized by VFS rules. Adding a duplicate is a no-op.

### VMHandle.remove_breakpoint

```python
vm.remove_breakpoint(line: int, path: str | None = None) -> None
```

Remove the specified location. A missing location is a no-op; the argument rules are the same as for adding.

### VMHandle.breakpoints

```python
vm.breakpoints() -> list[dict[str, object]]
```

Return independent dictionaries in the order they were added, each shaped like:

```python
{"line": 2, "path": None}
```

Breakpoints can be managed as long as the VM has not been disposed. Host breakpoint management has no target-specific count limit and does not count against target script resource metering.

### Hitting and resuming

- `path=None` matches the current main source and its functions; an explicit path matches the target's own entry and imported modules.
- A breakpoint location is constrained by both the target VM and the source identity, so it does not accidentally hit foreign code granted by another VM.
- Only actual statement entries are hit; blank lines, comments, non-starting lines of multiline statements, and a `pass` that produces no instruction do not hit.
- A hit happens before the first instruction executes, changes the state to `paused`, does not move the PC, and does not run the target's `except`/`finally`.
- `run()` returns normally at the breakpoint; the snapshot's `breakpoint` records the actual `line` and `path`.
- Calling `run()` or a stepping method from `paused` resumes and exempts the current breakpoint only once; reaching it again in a loop still hits.
- A pause does not propagate to ancestors.

## Snapshot

### VMHandle.snapshot

```python
vm.snapshot() -> dict[str, object]
```

Return the current host-safe snapshot without advancing execution. The snapshot contains only safe copies, with no operable VM handles; modifying the returned value does not modify the VM.

The host snapshot is a strict superset of the script's safe view:

| Field | Type | Meaning |
|---|---|---|
| `state` | `str` | The current VM state |
| `last_line` | `int \| None` | The most recently executed logical source line |
| `next_line` | `int \| None` | The next executable source line |
| `locals` | `dict` | A safe copy of the currently user-visible local values |
| `stdout` | `str` | The currently retained output |
| `error` | `dict \| None` | The safe diagnostic of the current error |
| `breakpoint` | `dict \| None` | The `line` and `path` when paused |
| `instruction_count` | `int` | The current instruction and size-scaled work |
| `vm_id` | `int` | The in-engine number, never reused |
| `parent_id` | `int \| None` | The parent VM's in-engine number; `None` for the root |
| `depth` | `int` | The nesting depth; 0 for the root |
| `child_count` | `int` | The cumulative number of directly created child VMs; disposing children does not decrease it |

`error` contains `kind`, `message`, `line`, `column`, and `frames`. Here `frames` is a list of dictionaries, each containing `function` and `line`, not `SericiteFrame` objects. The call stack exposes only the safe view of the VM the snapshot belongs to.

Complex values are subject to node and depth budgets; cyclic or repeated structures use placeholders. Records are represented as safe data with a `<record>` marker, and functions, modules, and handles are represented as display text. Snapshots contain no handles or internal context that could keep driving VMs.

The script snapshot has only the first eight common fields and cannot obtain host diagnostic fields such as `vm_id`.

## Lifecycle

### VMHandle.terminate

```python
vm.terminate() -> None
```

Mark a target in `ready`, `waiting_input`, or `paused` as `terminated`; in other states it is a silent no-op.

This operation only changes the current target and does not cascade-terminate descendants. The target can still be snapshotted, its stdout read, and `take_fs()` called, but it cannot accept `exec()`. Use `dispose()` when you need to destroy the whole descendant tree.

### VMHandle.dispose

```python
vm.dispose() -> None
```

Destroy the target in any state and all its live descendants, and release live-VM-count slots.

- It can be called in non-terminal states and does not require children before parents.
- A running target stops after the current instruction exits safely, without running the target script's `finally`.
- Repeated calls are no-ops.
- After the call, the target handle is invalid and other methods raise `runtime_error`.
- Already-consumed cumulative instruction, output, or memory budgets are not refunded.

A VM that becomes completely unreachable is eventually collected by Python's GC, including reference cycles, but the timing is not guaranteed. Dispose explicitly when you need a definite release point. For the timing of observing automatic collection, see the [observation reference](05-observation.md#garbage-collection-notifications).

### VMHandle.take_fs

```python
vm.take_fs() -> VFSHandle
```

Atomically take the attached VFS out of a terminal VM and return a new detached handle. Only `done`, `error`, `resource_exhausted`, and `terminated` are allowed; non-terminal states or a running VM are rejected with `runtime_error`.

After taking, the original VM can still be snapshotted, have its stdout read, and be disposed, but it loses file access and no longer accepts `exec()`. Functions defined by the original VM also cannot keep accessing the transferred workspace through the original VM. Disposing the original VM does not affect the taken-back VFS.

A target with no attached VFS is likewise rejected. On failure, ownership is unchanged. For the complete transfer rules, see [VFS and files](03-vfs-and-files.md).

## Host file management

The host `VMHandle` also provides `read_file`, `write_file`, `delete_file`, `rename_file`, `copy_file`, `make_dir`, `delete_dir`, `rename_dir`, `copy_dir`, `list_dir`, and `path_exists`, operating on the VFS currently attached to that VM.

These methods are a trusted host management channel, not a public proxy for script-side VM handles. For the unified signatures and limits, see [VFS and files](03-vfs-and-files.md#file-and-directory-methods).

## Host management and script metering

The host's `feed_input()`, breakpoint management, `VMHandle`/`VFSHandle` file operations, stdout/snapshot reads, and `dispose()` do not count against script resource metering. The file-count, per-file-byte, total-storage, and output-byte limits themselves still apply.

The actual VM instructions and dynamic operations executed by `run()`, `exec()`, `step()`, and `step_instruction()` are always subject to the VM's quotas. Host management being free does not mean script execution is free.
