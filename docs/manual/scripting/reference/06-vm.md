# VM

`VM` creates an independent Sericite execution environment inside a script. The child environment does not inherit the parent environment's local variables, module cache, input, output, or files.

A VM is not one-shot: `run()`, input waits, breakpoint pauses, stepping, and repeated `exec()` all drive the same VM, and module-level names and resource accounts persist. Create another VM when a brand-new environment is needed.

## Construction

```text
VM(source, ...) -> VM
VM(source=source, ...) -> VM
VM(entry_file=path, fs=workspace, ...) -> VM
```

`source` and `entry_file` must be provided exactly one at a time:

- `source` is the source string; modules resolve from the workspace root.
- `entry_file` is the path of an entry file in the workspace and must be provided together with `fs`. The entry is read and compiled at creation, and modules resolve from the entry's directory.

Missing both sources, providing both, or a wrong type raises `type_error`. An entry file must explicitly go with a detached VFS; entry reading or compilation failure does not consume that VFS.

When no `fs` is provided, an empty VFS is created. When provided, a successful creation moves the detached workspace exclusively into the new VM and invalidates the old handle; see [VFS](07-vfs.md).

### Non-quota options

| Option | Default | Contract |
|---|---|---|
| `fs` | `None` | a detached VFS; moved to the child VM on success |
| `addons` | `None` | a dict from strings to functions, granted through `__addon__` |
| `output_writer` | `None` | a function called after each child VM `print()` |
| `buffer_output` | `True` | whether to retain stdout; must be strictly `bool` |

Unknown options, an invalid addon table, writer, or option type raise `type_error`.

## States

| State | Meaning | Terminal |
|---|---|---|
| `ready` | not yet started, or ready to continue | No |
| `waiting_input` | waiting for input that may arrive later | No |
| `paused` | paused at a statement-entry breakpoint, with recoverable state | No |
| `done` | the current program completed normally | Yes |
| `error` | the current program terminated with an ordinary error | Yes |
| `resource_exhausted` | the current program terminated because a resource quota was exhausted | Yes |
| `terminated` | terminated by `terminate()` or cascade disposal | Yes |

After disposal the VM handle is invalid and no longer provides a readable `disposed` state; methods other than repeated `dispose()` raise `runtime_error`.

A terminal state does not mean the handle is invalid. A terminal VM can still be snapshotted, have its stdout read, have its VFS taken back, or be disposed. Other than `terminated`, a VFS already taken, and a running VM, states can usually accept `exec()`, but an exhausted quota may still refuse later work.

## Driving methods

### `VM.run`

```text
vm.run() -> str
vm.run(inputs) -> str
```

Drives the target until it completes, waits for input, hits a breakpoint, or fails. Returns the target's currently retained stdout string.

`inputs` must be a list or tuple of strings. The whole batch is validated and then added to the target's input queue; a target in `waiting_input` is woken. Input can also be provided line by line through `feed_input()`.

- A return does not guarantee the state is `done`; judge `waiting_input` or `paused` through the snapshot.
- `run()` returns the cumulative retained output, not just the text newly produced by this call.
- When the target errors, it propagates to the controller with the original kind; catchable errors are caught normally by the controller.
- A child VM's `resource_exhausted` can be caught by a still-live parent VM; exhaustion of the parent VM itself or an ancestor cannot be caught by that parent VM itself.
- With `buffer_output=False`, output is not retained, so an empty string is returned, but writer forwarding still happens.

### `VM.exec`

```text
vm.exec(source) -> str
```

Compiles and delivers new source, executing it in the same module scope. Returns only the buffered output newly produced by this delivery.

Retained content: module-level variables, functions and schemas, the imported-module cache, addons, the VFS, the module resolution root, the input queue, output configuration, breakpoints, and the accumulated resource account.

The old program that has not finished executing is discarded, including states that never started, are waiting for input, or are paused at a breakpoint; the old error and debug frame stack are replaced. Call `snapshot()` first when you need the old state.

Compilation happens before any state change. On compilation failure, the original program, paused state, and breakpoint bindings stay as they were. After a successful delivery, main-path breakpoints bind to the new main source by the same line numbers and do not hit functions left over from the old delivery.

A `terminated` VM, one whose VFS has been taken, or one currently being driven rejects delivery. `source` must be a string.

### `VM.feed_input`

```text
vm.feed_input(value) -> None
```

Adds one line string to the target's input queue. A target in `waiting_input` changes to `ready`, but this method does not actively execute the target; call `run()` or a stepping method afterward to continue.

### `VM.step`

```text
vm.step() -> dict
```

Executes one statement and returns a safe snapshot. Statements inside function calls and breakpoints may affect the actual stopping location. A target already in a terminal state does not advance and only returns the snapshot. A target in `paused` resumes execution, and the current breakpoint is exempted only once.

### `VM.step_instruction`

```text
vm.step_instruction() -> dict
```

Executes one Sericite internal instruction and returns a safe snapshot. The terminal-state and breakpoint-resume rules are the same as `step()`. Internal instructions are a debugging granularity, not a public operator API in script source.

### `VM.snapshot`

```text
vm.snapshot() -> dict
```

Returns the current safe snapshot without advancing execution. The field structure is in [snapshot](#snapshot).

### `VM.stdout`

```text
vm.stdout() -> str
```

Returns the target's currently retained cumulative stdout without advancing execution. With `buffer_output=False`, it returns an empty string.

### `VM.terminate`

```text
vm.terminate() -> None
```

Marks a target in `ready`, `waiting_input`, or `paused` as `terminated`. In other states it is a silent no-op.

The target can still be snapshotted and `take_fs()` called afterward, but it cannot accept `exec()`. `terminate()` only changes the state of this one target; use `dispose()` when you need to destroy the whole descendant tree and release resources.

### `VM.dispose`

```text
vm.dispose() -> None
```

Destroys the target in any state and all its live descendants, and releases the live-VM-count slots they occupy.

- It can be called in non-terminal states and does not require children before parents.
- A running target stops after the current instruction exits safely, without running the target script's `finally`.
- Repeated calls are no-ops.
- After the call, the target handle is invalid and other methods raise `runtime_error`.
- Already-consumed cumulative instruction, output, or memory budgets are not refunded.

Executing the disposal itself requires resources; when resources are insufficient, `dispose()` fails before actually deregistering. A VM that becomes completely unreachable is eventually collected automatically, including reference cycles, but the timing is not guaranteed. Dispose explicitly when you need a definite release point.

### `VM.take_fs`

```text
vm.take_fs() -> VFS
```

Atomically takes the attached VFS out of a terminal VM and returns a new detached handle. Only `done`, `error`, `resource_exhausted`, and `terminated` are allowed; `ready`, `waiting_input`, `paused`, or a running VM is refused.

To abandon a waiting session, `terminate()` first and then take it back. After taking:

- the original VM can still be snapshotted, have its stdout read, and be disposed;
- the original VM loses file access and no longer accepts `exec()`;
- functions defined by the original VM, even if already granted to other VMs, can no longer access the transferred workspace through the original VM's file functions;
- disposing the original VM does not affect the taken-back VFS.

A target with no attached VFS or a disallowed state raises `runtime_error`. On failure, ownership is unchanged.

## Output forwarding and buffering

Every VM has independent output configuration. The parent program can configure `output_writer` explicitly:

```python
def forward(text):
    print(text, end="")

program = VM("print(\"live\")", output_writer=forward)
program.run()
```

After each target `print()` finishes output handling, metering, and optional buffering, the writer receives a string containing this call's separator and `end`.

- The writer follows the addon definer-environment rules; calling the parent's `print()` can keep forwarding along the parent's output chain.
- The return value is ignored.
- A writer error propagates at the target `print()` that triggered it.
- The writer must complete synchronously; trying to pause through `input()` raises `runtime_error` at that `print()`.

By default `buffer_output=True`, and `run()`, `exec()`, `stdout()`, and snapshots retain output. Setting it to `False` still meters and forwards but leaves the buffered view empty. The configuration persists across `exec()`.

## Breakpoints

### `VM.add_breakpoint`

```text
vm.add_breakpoint(line, path=None) -> None
```

Adds a statement-entry line breakpoint. `line` must be a strict integer greater than zero; `path` is `None` or a logical path normalized by VFS rules. Adding a duplicate is a no-op.

`path=None` matches the current main source and its functions. An explicit path matches the target's own entry file and imported modules, not foreign code granted by another VM.

### `VM.remove_breakpoint`

```text
vm.remove_breakpoint(line, path=None) -> None
```

Removes the specified location. A missing location is a no-op; the argument rules are the same as for adding.

### `VM.breakpoints`

```text
vm.breakpoints() -> list
```

Returns a list of plain-data dictionaries in the order they were added, each being:

```python
{"line": 2, "path": None}
```

Breakpoints can be managed as long as the VM has not been disposed. There is no target-specific breakpoint count limit, but storage and method calls still consume the controller's general resources.

### Hitting and resuming

Only actual statement entries can be hit: blank lines, comments, non-starting lines of multiline statements, and a `pass` that produces no instruction do not hit; a line with multiple statements that each produce instructions can be hit separately.

A hit happens before the first instruction executes:

- the state changes to `paused`, and the PC, local variables, call frames, and stdout are preserved;
- `run()` returns normally, raises no exception, and does not run the target's `except`/`finally`;
- the snapshot's `breakpoint` field records the actual location;
- calling `run()`, `step()`, or `step_instruction()` from `paused` resumes and exempts the current breakpoint only once; reaching it again in a loop still hits;
- a pause does not propagate to ancestors.

## Snapshot

`step()`, `step_instruction()`, and `snapshot()` return the following fixed fields:

| Field | Type | Meaning |
|---|---|---|
| `state` | `str` | the current VM state |
| `last_line` | `int` or `None` | the most recently executed logical source line |
| `next_line` | `int` or `None` | the next executable source line |
| `locals` | `dict` | a safe copy of the currently user-visible local values |
| `stdout` | `str` | the currently retained output |
| `error` | `dict` or `None` | the safe diagnostic of the current error |
| `breakpoint` | `dict` or `None` | the `line` and `path` hit when paused |
| `instruction_count` | `int` | the current instruction and size-scaled work account |

`error` contains `kind`, `message`, `line`, `column`, and `frames`. `frames` is a list of dictionaries, each containing `function` and `line`. Across VMs, only the current target's own safe call stack is exposed.

Complex values are subject to node and depth budgets; cyclic or repeated structures use placeholders. Records are represented as safe data with a `<record>` marker, and functions, modules, and handles are represented as display text. Snapshots contain no handles that could keep driving child VMs.

## Limits

The constructor's quota keywords correspond one-to-one with the table below:

| Option | Default | What it limits |
|---|---:|---|
| `max_instructions` | 1,000,000 | instructions and size-scaled work |
| `max_output_bytes` | 1,048,576 | UTF-8 bytes of stdout |
| `max_frames` | 100 | call-frame count |
| `max_list_size` | 100,000 | slots in a single list/tuple |
| `max_dict_size` | 100,000 | items in a single dict |
| `max_string_bytes` | 1,048,576 | characters in a single string; the name keeps the historical byte wording |
| `max_int_bits` | 4096 | integer bit width |
| `max_total_bytes` | 67,108,864 | the approximate high-water mark of total memory |
| `max_descendant_vms` | 1000 | the whole live-descendant count of a single VM, excluding itself |
| `max_vm_depth` | 8 | VM nesting depth |
| `max_fs_files` | 1000 | the total number of VFS files that file operations can expand to |
| `max_fs_file_bytes` | 1,048,576 | UTF-8 bytes of a single file that can be written or copied |
| `max_fs_storage_bytes` | 67,108,864 | the approximate total VFS storage that can be expanded to |

When a VM creates a child VM, it can only tighten the inherited limits, not loosen them:

- Only `max_instructions`, `max_output_bytes`, and `max_total_bytes` accept `-1`, meaning no upper bound at this layer.
- Requesting `-1` inherits the ancestor's effective finite limit; it is infinite only when every relevant layer is infinite.
- Other quotas must be non-negative finite integers and do not accept `-1`.
- Setting `max_descendant_vms=0` forbids that VM from creating any descendant, without affecting its parent creating it.
- A child VM's instruction, memory, and creation consumption is also charged to its relevant ancestors; a finite ancestor is always a hard limit.
- Unlimited quotas only disable the limit check; they do not stop recording usage.

The defaults are for development and debugging, not a safety recommendation for running untrusted code. The controller should tighten quotas explicitly for the task.

The three file limits are constraints on the VM's operations and are not carried with the VFS. The actual call chain tightens them together; a constraint that refuses a change uses `file_limit_error`, unlike the `resource_exhausted` of execution-account exhaustion; see [file limits](04-files.md#file-limits-and-error-recovery).

## addon granting

```text
VM(source, addons={"public_name": function}) -> VM
```

Dictionary values can be functions defined by the current VM or already-held granted functions. Keys are valid identifiers that do not start with `__` and may collide with built-ins. If a direct import would rebind a local built-in, the receiver should use an import alias.

Child modules must import explicitly:

```python
def double(value):
    return value * 2

program = VM(
    "from __addon__ import double\nprint(double(21))",
    addons={"double": double},
)
print(program.run(), end="")
program.dispose()
```

```text
42
```

A granted Sericite function:

- keeps its definer's module variables, closures, and granted environment;
- its internal `print`, file functions, imports, and `VM()` still use the program environment where the function was defined;
- is subject to both the definer's and the caller's resource limits when called;
- shares records across VMs by reference, and field contracts remain in effect;
- can use parameter names for the receiver's keyword calls, but error text does not leak the definer's internal names and source line numbers;
- raises `runtime_error` when called after the VM that defined it has been disposed, even if the function has already been passed to another VM.

Granting a function grants the environment and capabilities it can access, including VM handles captured in closures and their control permissions. Grant only the functions the child program genuinely needs.
