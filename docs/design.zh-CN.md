# Sericite 设计说明

本文说明 Sericite 是什么、为什么存在、设计边界划在哪里。语言语法见[语言参考](language-reference.zh-CN.md)，引擎内部结构与当前实现状态见[架构说明](architecture.zh-CN.md)（[English](architecture.md)）。

## 1. Sericite 是什么

Sericite 是一门脚本语言，以及这门语言的执行引擎。语法上它借用 Python 的一个子集（写起来就是 Python 的样子），但源码会被编译成 Sericite 自己的内部指令，由 Sericite 引擎逐条执行——不经过宿主（即运行 Sericite 引擎的那个程序）的 `exec`/`eval`。

这门语言存在的理由只有一件事：**在语言自己的能力范围内，以极低的成本创建完全隔离的运行环境，并且这种环境可以任意嵌套。**

用一句话描述它的世界观：你位于一个宇宙中，你可以在当前宇宙里创建另一个宇宙；对你创造的宇宙而言你如同上帝，而你所在的宇宙也可能有它的上帝，但你不可能知道。

## 2. 为什么需要它：虚拟化的成本光谱

"在运行中的系统里再圈出一块隔离天地"并不新鲜，已有方案分布在一条成本光谱上：

- 硬件级虚拟化：模拟完整硬件，装操作系统，吃掉大量磁盘与内存。
- 容器级虚拟化：好一些，但仍要初始化一整套容器环境。
- 进程级隔离：依赖操作系统为每个进程独立管控权限。

进程级方案看似够用，但有两个根本问题。

**其一，进程这个单位太重，操作系统管不过来。** 一个进程发起一次 IO、一次系统调用，摆到内核面前的"菜单"都非常复杂。内核没有充分证据判断某次调用是不是在干坏事，也就无法事无巨细地治理。结果是：OS 管控进程这件事本身漏洞频出，提权时有发生。

**其二，内核态方案不够轻，而历史早已证明用户态更便宜。** 回想并发的演进：有了进程为什么还要有线程？因为创建进程昂贵、进程间传数据昂贵，干什么都昂贵。有了线程为什么还要有协程？因为线程的切换仍要从用户态陷入内核态，当互联网带来成百上千的并发任务时，还是太贵。每一次演进的方向都相同：**能在用户态解决的事，不要推给内核；不要把 OS 这个已经不堪重负、满身窟窿的管家当成万能保姆。**

顺着这个方向再走一步，就是 Sericite 的位置：**一种完全在用户态内、在语言自身内部实现的虚拟化。** 在 Sericite 里创建一台子虚拟机，代价应当和 Lua 里创建一张子表一样自然。隔离不再依赖模拟硬件、初始化容器或申请进程，而是语言运行时的内建能力。

或许有人会问：这事以前没人做过吗？诚实的回答是：做过——而且几乎一模一样。Tcl 自 7.5 版本（1996 年）起就把安全解释器做成了语言内建，其源头是 Borenstein 与 Rose 在 1992 年为"主动邮件"实现的 Safe-Tcl。安全解释器默认零能力；master 通过 alias 机制把受控能力逐条授予回去；安全解释器还能再创建自己的子解释器，形成层级。"隔离是语言的第一类操作、可嵌套、能力显式授予"因此是一套被验证过三十年的机制，而不是新的空想。

但 Safe-Tcl 走了一半就停下了：资源治理与 kill-key 在 1998 年被明确承诺，却延迟多年才部分兑现，且从未成为跨层级的配额会计。Sericite 在这条血脉里的位置是精确的：保留被验证过的内核（零能力默认、显式授予、递归嵌套），补上缺失的另一半——配额树，以及把子 VM 当作可检查对象（单步、快照、终止）。WASM 运行时、microVM 沙箱、gVisor、Starlark 各自占据成本光谱上相邻的点，完整对比见[先例与相关工作](prior-art.zh-CN.md)。

为什么强调"任意嵌套"而不只是一层？因为隔离需求本身是递归的：你的程序拿到一段不可信脚本要隔离执行，而这段脚本运行起来之后，自己又要执行它动态获得的代码。现实里的不可信性层层传递，隔离机制就应当能层层跟随，而不是只守大门。

## 3. 核心理念

### 3.1 最小、轻量化、完整的运行隔离

Sericite 的隔离环境（VM）默认什么权限都没有。内建能力被刻意压到极少：

- 基础输入输出（每个 VM 独立的虚拟 IO）；
- 纯内存的虚拟文件系统（纯文本，物理上碰不到真实磁盘）；
- 创建子 VM。

虚拟文件系统就是内建能力的上限。到此为止，不再多给。

### 3.2 能力靠授予，不靠内建

VM 当然不是只能拥有内建能力——但那走另一条路：**能力授予（FFI）**。宿主可以用宿主语言（当前参考实现是 Python）写好函数，注入给它创建的 VM；同理，任何一层 VM 也可以在自己的世界里写好函数，授予给它创建的下一层 VM。能力沿创建链逐层、显式地传递，默认为零。

为什么不给 VM 内建网络访问？因为这条路的终点是荒谬的：内建了 HTTP，那裸 TCP 呢？UDP 呢？蓝牙、串口、光盘、麦克风、摄像头呢？——需要适配的东西无穷无尽。就算真的全部适配，每台 VM 都长出自己的网络逻辑、蓝牙逻辑、各种设备逻辑，那就等于在语言内部重新模拟一整套物理硬件，恰恰背叛了"最小、轻量化"的立身之本。

所以网络访问之类的能力，正确形态是由外部用 FFI 注入，而不是在引擎里内置。

这套机制已在原型中落地：宿主用 Python 函数注入 root VM，任何一层 VM 也可以把自己 `def` 的函数（或上一层已授予自己的函数）授予给下一层。跨越宿主边界时，参数与返回值都做双向深拷贝，且只限纯数据类型——VM 与宿主之间不存在共享的可变对象。宿主回调以契约 kind 的 `SericiteError` 报告失败；契约之外的宿主异常会使 VM 以不可捕获的 `host_error` 终止。完整异常契约见[宿主参考](host-reference.zh-CN.md)第 5.3 节。

### 3.3 安全边界的划分

这套设计把安全责任切成界限分明的两块：

- **引擎负责隔离本身成立。** 子 VM 无法读写父级变量与文件、无法感知自己嵌套在第几层、无法触及宿主对象与反射入口、无法绕过资源配额。这是 Sericite 的设计承诺。
- **能力的实现者负责能力本身的安全。** 你通过 FFI 授予 VM 一个函数，这个函数内部是否安全，由你来保证。引擎的理念是把内核保持到最小，至少不把雷埋在自己内部。

### 3.4 结构跨层，名字层本地

record/schema 的设计（`class` 定义结构契约、点号成员访问）遵循一条与能力授予同源的戒律：**跨层的只有结构；名字、能力、状态，一律要在当前层的代码里有一个看得见的门。**

这条戒律有三个推论：

**不引入名义类型。** 名义身份由创建事件决定，在层层嵌套、逐层授予的世界里处处撞身份墙——父 VM 的 `Point` 与子 VM 的同名同形状类型算同一个吗？结构语义下 schema 按字段集与契约比较，天然跨层可比，这个问题整体不存在。同时沙箱的输出必须是可枚举的纯数据，名字不污染值，这个不变量也保住了。

**标签是编译期、作用域本地的诊断信息，永不进入值。** 名字是词法事实，不是值的事实：一个值逃逸出定义它的作用域后（工厂返回、跨 VM 传递），它本来就没有名字。如果值身上烙着长生不死的名字，子层报错时就会显示一个子层源码中从未出现过的符号——子 VM 的错误消息是可被 `except` 捕获的数据，这个名字就成了一条谁都没有显式打开的信息信道。随值旅行的名字迟早会被当成身份来用（比较、分派、序列化），名义类型就从后门回来了。所以类名与注解名只活在编译期、只用于报错文本，出作用域即擦除。每一层在自己的入口显式命名（`r2: T2 = make()`）；命名是接收方的本地行为，不是随货附赠的遗产。

**授予函数的报错也守这条边界。** 被授予的函数在子 VM 中执行时保留定义方的完整环境（这是显式授予的能力），但它的报错文本只使用授予名（`functions={"f": ...}` 里的 `f`）与结构描述——定义方的函数名和类型标签不出现在子层。门上的名字是门的一部分；门里东西的内部名字不是。

## 4. Sericite 与 LLM 的关系

必须澄清一个常见误读：**Sericite 不是"给 LLM 用的工具"。**

真实关系是这样的：LLM 应用是 Sericite 当前最直接、最现实的驱动力——当系统需要动态地面对成百上千段生成脚本、且它们都要被隔离执行时，"低成本、可嵌套的隔离"从锦上添花变成了刚需。Sericite 正是被这个时代需求催生的。

但这层关系是单向的：**场景选择了 Sericite，Sericite 的设计却不耦合场景。** Sericite 的引擎不认识 LLM，没有任何与 LLM 相关的内建，也不以任何形式依赖某个模型服务；脱离了 LLM 场景，"低成本、可嵌套的用户态隔离"这个命题依然成立。你可以在应用层将 Sericite 引擎通过一个形如 sericite_exec 的工具挂在某个 LLM 服务的工具列表里，Sericite 引擎本身并不在意你会怎么用它。

## 5. 原型与设计：区分"要去哪里"与"走到哪了"

阅读本项目时，请始终区分两个层面：

- **设计**：上面第 1～4 节描述的目标与边界。这是项目要去的地方。
- **原型**：仓库里的代码是参考实现（代号 Sericite-PY），用 Python 实现。它是施工过程稿，用来回答"这个设计理念落实下来，语法和使用上到底长什么样"，把语言的蓝图定下来。

因此，"原型当前尚不完整"与"设计是否成立"是两回事。原型缺的功能会继续补；原型的实现限制（比如它目前与宿主同进程）是施工阶段的状态，不是对设计理念的否定或退让。

同样请区分目标与实证的还有"成本"：第 2 节所说的"创建子 VM 像建一张表一样便宜"是设计目标与努力方向，但"便宜"已有初步实测支撑——当前 Python 原型中，脚本内 `VM()` 创建一台子 VM 约 0.088 ms，与创建一个线程同数量级，比进程便宜一到两个数量级。需要强调：这是原型参考实现的实测数字，不是性能承诺。完整实测数据与复现脚本见[架构说明](architecture.zh-CN.md)第 6 节；引擎日后重写时需重新测量。

至于未来的发布形态——引擎底座是留在 Python，还是迁移到其他语言、产出独立的二进制运行时（比如一个 `sericite` 可执行文件）——目前不做结论。初步判断 Python 作为底座并不差；即便日后迁移，功能形态也大体相当：Sericite 内建能力有限，其余靠与其他语言协作注入。无论如何，都要先有完整原型作为设计图，才谈得上在别的底座上按图重建。

## 6. 名字由来

Sericite 即绢云母，云母族中晶粒最细的一支：细小的丝绢鳞片层层叠置，每一片仍是完整的一层，且与所有云母一样是电绝缘体。这个名字说出了这门语言的三个设计承诺：层叠、绝缘、轻量。

- **层叠**：绢云母的细鳞片层层相叠，每一片仍是完整的一层。这对应了"嵌套虚拟化"的设计目标。
- **绝缘**：绢云母是电绝缘体，层与层之间不导电。这对应了"隔离"的设计目标。
- **轻量**：云母族中最细的鳞片，轻盈且透明。这对应了"极低成本"和"无感知嵌套"的设计目标。

需要说明：本项目曾短暂名为 Mica/MicaLang，后发现该名字已被多方占用——包括一门活跃开发的商业语言，其 Docker 镜像发布在 `micalang` 命名空间下——遂更名。本项目的仓库与安装名是 `sericite`。

## 7. 一句话总结

Sericite 借 Python 的语法外壳，做了一件 Python 做不到的事：**把"创建一个完全隔离的宇宙"变成一句普通脚本语句，便宜到可以随手使用，并且层层嵌套、互不感知。** 它是一门以"用户态虚拟化"为核心命题的语言，不是 LLM 的附属工具，LLM 时代只是让这门语言要解决的问题变得更加醒目了。
