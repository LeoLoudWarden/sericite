## 第二阶段建议

### 1. 先固化现有回归测试

用标准库 `unittest` 即可，不必增加依赖。至少覆盖：

- 根 VM 和子 VM 的运行、单步、输入暂停与恢复。
- 父子 VM 的变量及 IO 隔离。
- 非法 AST、属性和权限拒绝。
- 当前三个 CLI 示例的精确输出。

这样后面调整执行内核时，不会破坏第一阶段成果。

### 2. 将顺序 AST 执行改为内部指令流

不一定要叫“字节码”，也可以只是一个简单的内部指令列表，例如：

```text
LOAD_CONST
LOAD_NAME
STORE_NAME
BINARY_ADD
CALL
JUMP_IF_FALSE
JUMP
```

VM 继续持有程序计数器和操作数栈，每条内部指令都可以：

- 单步执行；
- 计入执行配额；
- 暂停和恢复；
- 报告对应的 Mica 源码行号。

然后只增加少量必要语法：`if`、`while`、比较运算和布尔运算。暂时不用急着支持函数、类和模块。

**关键点是：不要把整个 `while` 当成一次 `step()` 执行完。**

### 3. 加入最小资源治理

优先实现三个容易定义、容易验证的维度：

- `max_instructions`：最大内部指令数；
- `max_output_bytes`：单 VM 最大输出量；
- `max_child_vms`：可创建的子 VM 数量。

同时补充：

- `terminate()`；
- `resource_exhausted` 和 `terminated` 状态；
- 结构化错误，包含资源类别、逻辑行号和 VM ID。

内存配额可以稍后做。CPython 同进程内很难精确限制所有内存分配，不宜过早作出安全承诺。

## 引擎现在"真"在哪里

**内部指令流**（`mica/isa.py` + `mica/compiler.py`）：源码不再被 AST 直接走，而是先经白名单校验、再编译成 20 条栈式指令（`LOAD_CONST`、`BINARY_OP`、`JUMP_IF_FALSE`、`CALL`、`RETURN` 等）。每条指令带行号，每个语句首条指令有 `stmt_start` 标记。

**自己的运行循环**（`mica/engine.py`）：`Frame{code, pc, stack, locals}` + 统一调度循环。`run()`、语句级 `step()`、新增的指令级 `step_instruction()` 共享同一条 `_execute_one` 路径——`step()` 就是"执行到下一个 `stmt_start`"，所以 while 循环体每次迭代都天然可单步。

**值语义由引擎定义，不继承 Python 隐式行为**：bool 不参与算术；int/float 混合提升、`/` 恒为 float；跨类型排序比较报 `type_error`；除零报 `zero_division`；`int("abc")` 报 `conversion_error`。错误分类共 11 种，全部带行号。

**函数**：`def`/`return`/递归，独立帧局部作用域（可读模块级变量）。

**资源治理建立在指令计数上**：`MicaLimits` 五项配额（指令数、输出字节、帧深度、子 VM 数、列表大小），死循环被 `max_instructions` 掐死在 `resource_exhausted` 状态，`terminate()` 可随时终止 VM。子 VM 继承父级配额。

## 值得一提的 bug

初版 `_call` 先弹栈再调原生函数，`input()` 输入不足挂起时栈已损坏，恢复后直接出错。改为"先调用、成功后再提交栈变更"——这正是指令级挂起语义的关键细节。

首先，不要“对接到 [...]”。
都写了refs，什么意思？就是参考用的。这是以前的一个小工具，是“[...]”的附件，用于解释问题的。它只是一个toy-of-explain。

[...] 的实现和 mica 不能混为一谈。
你需要厘清一个概念问题，什么是LLM侧对接？
定义是：有一个类openai api的服务器，我们有message list，发给服务器request，服务器回我们respond。，我们解析respond。是文本是工具调用还是别的什么，按自己的逻辑处理。

```

respond = llm_api.gen(meassage, tools, 温度等可选项)
```

在这个定义下，[...] 在做什么？
它提供了一组 file_read/list/... 的抽象，可以作为tools，包含在request中。
AI就可以在respond中选择 "tool_use file_read/list..."，可以安全地读一个虚拟的，安全隔离的文件系统，保证：

```
  file_list
  ...

  mica_exec
  ...
```

注意层次问题：
file_read/list 等，是**给AI的适配工具**，是 llm-server-request-respond 层次上的概念！
mica 不是**给AI的适配工具**，mica_exec 才是！

## 三项工作

**1. try/except**（`mica/compiler.py` + `mica/engine.py`）
- 语法：`except zero_division:` 按 kind 过滤、`except file_not_found as e:` 绑定消息字符串、裸 `except:` 兜底
- 实现用 CPython 3.11 式**异常表**（`CodeUnit.handlers` 记录 pc 区间），正常路径零开销，break/return 穿越 try 不用特殊处理；编译器新增静态栈深度分析（带一致性断言），捕获时安全截断求值栈
- 异常可跨函数帧传播，也可跨 VM 传播（父 VM 的 try 能捕获子 VM `run()` 抛出的错误，kind 保留）
- `resource_exhausted` 和 `internal_error` **不可捕获**——配额不能被脚本吞掉

**2. VM 套 VM**（去层级 + 资源配置）
- 删除 `allow_vm` 和对外 `layer`：快照、repr、错误位置都不再暴露层级，内部 `depth` 仅服务于配额（`max_vm_depth=8`）。每个 VM 都是"自己的根"
- 新增关键字实参（`CALL_KW` 指令），`VM(code, max_instructions=...)` 可配置全部八项配额，**只能比父级更严**（`min` 钳制）
- **祖先记账**：子 VM 每条指令计入所有祖先的配额计数，整棵子树总开销有界

**3. 每 VM 虚拟文件系统**（`mica/vfs.py`，全新实现，未碰 `mock_fs_tools.py`）
- 平坦 `{路径: 文本}` 字典，目录隐式，路径规范化纯字符串运算——结构上不可能触达宿主磁盘
- 脚本内建 `read_file`/`write_file`/`list_dir`/`path_exists`；错误 kind `file_not_found`/`is_directory`/`not_directory` 正好被 try/except 过滤——印证了"异常先行"的顺序
- `VMHandle` 同名方法让父 VM/宿主在 `run()` 前预置文件、运行后取回产出——"可配置隔离工作空间"落地（见 `examples/vfs.mica`：父写配置 → 子读配置写结果 → 父取回，且父自己的 FS 里不存在该文件）

## 问题 1：demo 的容错缺口（崩溃的直接原因）

`mica_exec` handler 里只有 `vm.run()` 包了 `try`——模型的代码如果在**编译期**就被拒（比如这次的 `IfExp`），`create_root` 抛的 `MicaError` 直接裸奔到宿主，整个 demo 进程死掉。
