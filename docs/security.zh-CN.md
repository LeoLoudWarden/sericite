# Sericite 安全模型

本文说明 Sericite 的威胁模型：引擎保证什么、不保证什么、目前已知的限制，以及如何报告安全问题。**如果你打算用 Sericite 执行不可信代码，请先读完本文。**

## 1. 威胁模型

Sericite 面向的场景是：宿主程序拿到一段**不完全可信的脚本**（例如 LLM 生成的代码、用户提交的脚本），需要执行它，但不允许它读写宿主状态、消耗无限资源、或感知自己身处何种环境。

防御分两层，责任也分两层：

- **引擎负责隔离本身成立**（本文第 2 节）。
- **能力的实现者负责能力本身的安全**：你通过 FFI 授予 VM 的函数，其内部是否安全由你保证。引擎的理念是把内核保持到最小，以减少语言内部的可利用弱点。

## 2. 引擎保证什么

按设计承诺（并有回归测试覆盖），VM 内的脚本：

- **看不到**未授予的父级变量、父级文件、宿主对象、Python 反射入口；
- **感知不到**自己嵌套在第几层，错误与调试视图只含逻辑源码位置与安全值，不透传宿主 traceback 或真实路径；
- **绕不过**资源配额：指令、内存、输出、调用深度、容器大小、字符串与整数位宽、文件、子 VM 数量与嵌套深度均有上限，且子 VM 的消耗计入所有祖先（字段清单见[宿主参考](host-reference.zh-CN.md)第 2.2 节）；
- **吞不掉** `resource_exhausted` 与 `internal_error`——这两类错误不可被脚本的 try/except 捕获，配额不能被脚本吃掉；
- **收不到**宿主异常的原文：契约之外的宿主异常只会使当前 VM 以不可捕获的 `host_error` 终止——消息只含宿主异常的类型名、绝不含异常文本，脚本无法捕获它，也无法借它探测宿主异常类型。完整 FFI 异常契约见[宿主参考](host-reference.zh-CN.md)第 5.3 节；
- **看不到**其他层的名字：record/schema 不携带任何名字；类名、注解名等编译期标签只在定义它们的 VM 的报错中可见。授予函数在你的 VM 里报错时，使用授予名与结构描述，定义方的函数名与类型标签不会出现。

隔离成立的前提是执行路径唯一：所有 VM 由同一个引擎经同一条调度循环驱动，脚本无法绕过编译器白名单触达宿主。

## 3. 引擎不保证什么

以下每一条都同等重要，请在使用前评估：

1. **当前引擎基于 Python 实现，与宿主同进程运行。** 引擎或 CPython 自身的实现缺陷在理论上可能打破隔离。Sericite 尚未经过正式的外部安全审计——0.1.0 之前只做过内部与第三方的对抗性审查（见第 4 节）。**对真正的对抗性代码，不要把 Sericite 当作唯一的隔离边界**：生产部署应在 Sericite 之外再套一层 OS 级隔离（独立进程、容器等）。Sericite 负责的是语言层的行为约束与资源治理。
2. **宿主函数的执行耗时与内存不按指令计费。** FFI 函数是可信代码，其 CPU/内存开销由宿主自律；恶意或失控的宿主函数不在配额覆盖范围内。
3. **成本模型是近似值。** 内存总账按近似字节记账、只增不减；O(n) 操作按规模折价计入指令数。它防的是"无界增长"，不是精确计量。
4. **配额默认值不是安全值。** 默认值面向开发调试，执行不可信代码时应显式收紧。
5. **授予函数就是授予其定义方状态的能力。** VM 间授予的 sericite 函数按引用保留定义方的模块变量、闭包 cell 与已授予函数环境——函数值自带它的整个世界：定义方可达的状态、IO/VFS 与子 VM 能力。世界服务仍解析回 home，执行由 home 与 caller 的联合因果路由约束，共享祖先只计一次。record 也经授予函数跨 VM 按引用传递：传出 record 等于共享其载荷的可变状态。只授予你允许子 VM 影响的函数与状态。详见[架构说明](architecture.zh-CN.md)与[宿主参考](host-reference.zh-CN.md)。
6. **VM 句柄的显示文本暴露引擎全局 VM 计数。** `print(sub)` 会显示 `<VM id=N state=...>`，其中 `id` 是引擎范围内递增的计数器。脚本可借此推断引擎累计创建过多少 VM——这是已知信息边界。该显示形式未来可能调整；已知方案无法同时做到低开销、不引入第三方库、不损失调试便捷性。
7. **CLI 的 Python 能力配置完全位于沙箱之外。** `--capabilities` 文件及其第三方依赖拥有完整宿主权限，必须由操作者显式信任，不能由模型或脚本选择。主源码和 include 仍在 VM 中运行，只能使用显式授予的能力；配置的 `files` 也只写 root 内存 VFS。详见 [CLI 参考](cli-reference.zh-CN.md)。

## 4. 已经过的审查

原型在 0.1.0 之前经过了一轮对抗性安全审查（内部独立审计 + 第三方独立视角），场景设定为"LLM 生成任意恶意代码经 `sericite_exec` 执行"。审查覆盖：隔离逃逸（白名单/dunder/属性访问）、拒绝服务（无界资源增长、快照放大、树状创建子 VM 的复利）、信息泄漏（FFI 消息、错误视图、快照内容）、编译期攻击（递归爆栈、超长源码）。发现的问题均已修复并固化为回归测试。

0.4.0（record 与注解契约）发布后经过了同标准的差分复审，覆盖：属性派发的封闭性、跨 VM 标签泄漏、契约检查的配额计费、宿主内部信息泄漏。发现的问题在 0.4.1 修复并固化回归测试（详见 CHANGELOG）。

出于负责任披露的考虑，具体攻击载荷不在公开文档中列出。如果你需要评估某类攻击是否已覆盖，欢迎开 issue 或私下询问（见下节）。

## 5. 已知语义偏差

出于原型取舍的考虑，引擎有一些与直觉或 Python 不完全一致的已知语义偏差：不是安全漏洞，但编写依赖精确语义的程序时应当知道。完整清单见[架构说明](architecture.zh-CN.md)的"已知边界"一节。

## 6. 报告安全问题

请使用 GitHub 的 Private vulnerability reporting 私下报告（仓库页面 → Security → Report a vulnerability），修复发布前请勿公开细节。属于引擎责任范围的问题示例见根目录 [SECURITY.md](../SECURITY.md)。

## 7. 使用建议

- 执行不可信代码时，为每层 VM 显式设置配额，不要依赖默认值。
- 只授予脚本实际需要的能力；授予函数内部自行做输入校验与资源限制。
- 把 Sericite 当作多层防御中的语言层，而不是唯一边界。
